Seam 03 · The tool boundary

Tools and context.

A verb is the unit of work the agent invokes: run(input, ctx) returns a ToolResult payload, and that is the whole of it — pure. The context ctx is a read-only ambient input — the pre-staged request, computed once by the boundary as a bounded projection of committed truth. A domain verb and a presentation verb are the identical mechanic: everything is a tool, even the UI — and every one of them signs.

▸

The seam at a glance

The eight slots, the same shape as every other seam. Read these, then the deep-dive below.

The seam
A verb — the unit of work the agent invokes. Its job: run(input, ctx) turns the agent's intent into a ToolResult payload, a pure function of input and a read of ctx. One registration supplies both of the boundary's maps: name → ToolResult, and name → Command.
Each side
Inner: the ctx — the committed State plus the bounded Context the reasoner saw — and the agent's intent expressed as input. Outer: the boundary that gates, folds and signs the returned payload. Same on both: a domain verb (setPriority) and a presentation verb (focusTicket) are one mechanic, not two.
What crosses
In: the decoded input, plus a read of ctx. Out: a ToolResult DTO, returned. Forbidden: a verb that mutates ctx, returns a live handle / entity / socket, performs an effect — or names an Actor, an Authority or a Signature. None of those may cross, and the last one cannot even be declared.
Direction
Source dependency points inward — a verb depends only on ctx's read-only shape and on the result types; ctx names nothing about the verb. Results flow outward as a returned payload — never written back into ctx.
The inversion
ctx is computed-by-the-boundary, read-only-to-verbs; the result leaves via the return value and is folded at the boundary. The agent reaches state through data it returns, never through a reference to a store it holds and mutates.
Why it exists
So a verb is tested by a direct call — no model, no surface, no mock of a mutable context. And so adding a capability is a bounded, local edit: two cases, a registry entry and a fold arm, all inside one folder, and the same four whether the verb touches the domain or the interface.
What breaks
A verb that writes its result into ctx (or a shared store) instead of returning it: the fold never sees it, the bus never records it, and the re-fold diverges from the run — Hidden State Coupling. A verb that reports who is asking is worse: it silently becomes a second authorship value nothing reconciles.
The test
setPriority.run({4118, High}, ctx) == SetPriority(4118, High) — by direct call, no doubles. And projectContext(state, staged, bounds) tested the same way: literal state in, assert the Context out, assert that the window the caller passed holds at 500 tickets.
A

What it is

The seam is a verb: the unit of work the agent invokes. The model emits an intent — “set ticket 4118 to High” — as a structured input, and the seam answers with a payload. The whole of a verb is one pure function, run(input, ctx), that takes the decoded input and a read-only context and returns a ToolResult. It reads; it computes; it returns. It does not mutate, it does not reach out, it does not record:

verbs — verbatim from the assembled programpseudocode
// A DOMAIN VERB — pure. Reads read-only ctx, returns a payload, mutates nothing.
VERB setPriority = Reversible {
  input = { ticket: TicketId, level: Priority }
  run(input, ctx) -> SetPriority(input.ticket, input.level)
}
// A PRESENTATION VERB — the SAME mechanic. Also pure, also folded, also signed.
VERB focusTicket = Reversible {
  input = { ticket: TicketId }
  run(input, ctx) -> FocusTicket(input.ticket)
}
// A GATED VERB — Irreversible cannot be constructed without saying where its Request lives.
VERB confirmEscalation = Irreversible {
  input = { ticket: TicketId }
  run(input, ctx) -> ConfirmEscalation(input.ticket)
  requestedBy(s, r) = (s.statusOf(r.ticket) as? Escalating)?.requestedBy
}
// … and two more of the same shape: requestEscalation (Reversible) and setPanel (Reversible).

Three verbs, one shape. Each derives its payload from input, may read ctx, and returns a ToolResult and stops. Two details are worth pausing on. First, the classification is part of the registration: there is no default to fall into, and Irreversible cannot be constructed without naming the state where its matching Request is recorded — so “is this action reversible?” is a reviewed row rather than something a reader has to infer. Second, notice what confirmEscalation does not do: it does not decide whether the confirm is permitted. It reports the ticket and hands the question to the boundary, which is the only place the answer exists. The payloads any verb may return are one closed set:

tool results — the DTOs a verb may returnpseudocode
sealed ToolResult(tool: ToolName) {
  SetPriority(ticket: TicketId, level: Priority)
  RequestEscalation(ticket: TicketId)
  ConfirmEscalation(ticket: TicketId)
  FocusTicket(ticket: TicketId)
  SetPanel(panel: PanelId, visible: Bool)
  Unhandled(note: Text)              // no registered verb, or an input that failed to decode
  Refused(reason: Text)              // the boundary gate said no — committed, so it re-folds
}

The parent declares tool, and that one field is why the set is navigable. The verb's name is the discriminant here, the case name in Command, and the key of the registry — one name per verb, all the way through — so “the gate keys off names” is literally true rather than a figure of speech. Read the last two cases as part of the vocabulary, not as error handling: a name the registry does not know becomes Unhandled, a denial becomes Refused, and both are folded and committed like any other outcome. That is what lets the fold be exhaustive with no catch-all — see seam 01.

What is missing from every case, and why

No variant carries an Actor. None carries an Authority or a Signature either, and none may gain one. The reason is a matter of ordering rather than taste: a verb runs at line (3) of the boundary, and the stamp is minted at line (4). A verb asking “who is calling me?” is asking a question that has no answer yet, and the only way to give it one is to invent a second authorship value alongside the real one. So the field does not exist, in the result or in ctx — which is the difference between a rule and a mechanism.

The context — ctx — is the other half of the seam, and the more easily mistaken one. It is a read-only ambient input with exactly two fields, state and context: the committed snapshot, and the bounded projection the reasoner was shown. It is computed once by the boundary before the step's verbs run, and exposed to them as immutable. It is the pre-staged Request Model: in Clean Architecture the controller hands a Request Model across the Input Port at call time; here the boundary has already derived everything the verb needs as ambient data before the step, so the verb merely reads it. The Input Port proper is the verb's run signature — the inner-side seam the agent invokes; ctx is the request data, staged rather than passed across at call time.

B

A presentation action is a verb too — the symmetry

The headline of this architecture is that everything is a tool, even the UI, and this seam is where that claim is either true or hollow. It is true here, exactly, because setPriority and focusTicket are the same mechanic — not merely the same shape. One mutates domain meaning (a ticket's priority); the other rearranges the interface (which row is focused, which panel is open). Both compute a ToolResult and return it; both are gated, folded, signed and committed by the identical path; and both leave the actual change to the fold and the projection downstream.

setPriority · a domain verb

Input is the agent's intent over the domain. run returns SetPriority(ticket, level) — a fact, not a write. The fold validates it against current state and turns it into a new State plus a LogDecision effect. It signs.

focusTicket · a presentation verb

Input is the agent's intent over the surface. run returns FocusTicket(ticket) — also a fact, not a write. The same gate, the same fold, the same bus, the same sites to add it — the same four declarations, and not one fewer for being about the surface. It signs too.

Because the mechanic is identical, a presentation action and a domain action are peers: each is a verb, each returns a ToolResult, each mints a Command and is recorded on the same bus. There is no second code path for “the UI doing something” and no cheaper registration for it — the surface emits an Action, the agent emits an Action, and both join the one stream. This is why the slogan is a data model and not a metaphor: the presentation verb is not like a domain verb, it is one. Map this to Clean Architecture and each is invoked across the same kind of Input Port — the run seam a caller crosses to reach a use case — the only difference being which kind of intent the caller is expressing.

Why a presentation verb signs, and where the ephemeral line actually falls

It is tempting to exempt interface verbs from signing — to let them fold into surface state and skip the Command, on the grounds that layout is not truth. Do that and you have bought a marginally cheaper verb at the price of two tool mechanics, which is worse for composition and worse for the story you tell about blast radius, not better. It also makes the headline false: a human tap and an agent call no longer resolve to the identical Command if one of them mints no command at all. And an agent that can show, hide, reposition and restructure an interface — auditably, replayably — is one of the strongest things this architecture offers; unsigning those verbs deletes precisely that.

The real axis is not UI-versus-domain, it is decision versus ephemera, and the test is one sentence: if losing this field on a re-fold would change what the system believes or what the artifact contains, it is truth — fold it. A deliberate repositioning passes that test and belongs on the bus; someone will eventually ask why the escalation button disappeared. A hover, a scroll offset, which accordion this browser tab has expanded, unsubmitted text in a box — none of those pass it. They never enter a verb, never fold, never sign, and live only in the presentation block's own ephemeral view-state. Volume, not kind, is what 5.4's “discrete, auditable, low-frequency action” is about: a repositioning is one; a scroll offset is not.

The same DTO law as seam 02

What crosses out of a verb is a ToolResult — plain data, a member of a closed sealed set. Never an entity, never a live Ticket object the boundary could mutate, never a socket or a file handle. The verb answers the question “what happened?” with a value, and hands that value back. Everything that acts on the value happens later, at one seam, where it can be recorded and replayed.

C

The context is a projection — the third pure map

Two projections of State have already been named in this example: project, which produces the view a person sees, and the fold, which produces the truth itself. There is a third, and it is the one most easily left as an accident: what the reasoner sees. It has the same right to a name, a type, a bound and a test as the other two, and it gets them here.

the context projection — verbatim from the assembled programpseudocode
data StagedInput = { source: Text, body: Text }        // untrusted perceived content — one per turn
data Context     = { staged: [StagedInput], lines: [Text], notices: [Text] }   // ORDERED off-bus fixture (book 6.11)
MAX_CONTEXT_LINES = 8 ; MAX_CONTEXT_NOTICES = 8        // the SHIPPED DEFAULT window, not the law
data ContextBounds = { lines: Int, notices: Int }       // the window, as ONE value the root wires
SHIPPED = ContextBounds(MAX_CONTEXT_LINES, MAX_CONTEXT_NOTICES)

projectContext(state, staged, bounds = SHIPPED) -> Context:   // PURE. Recomputed each step.
  Context { staged:  staged,
            lines:   ticketLines(state).takeLast(bounds.lines),
            notices: state.notices.takeLast(bounds.notices).map(summarize) }
render(context) -> Text                                // the exact text the reasoner sees — and a fixture

Three properties, and each rules out a specific way this seam usually rots.

It is a projection, not an accumulator. projectContext is a pure function of committed State plus the ordered inputs staged for this turn. It is recomputed from scratch at line (2) of every step and never appended to. A running buffer that the loop pushes onto is the natural thing to build and the wrong thing to have: it becomes a second source of truth that no fold wrote, that no bus recorded, and that no re-fold can reconstruct. Here there is nothing to reconstruct — you recompute it, and the same State gives the same Context, always.

It is bounded, by declaration. The caps are named in the source as the shipped default and travel as one value the composition root may set, and the artifact contributes a count rather than its content. The third parameter is defaulted, exactly as it is in both reference ports, which is why every two-argument call below is still a legal call — a caller that says nothing has inherited the shipped window, and one that passes a window reaches every block. So the reasoner's input does not grow with session length: a thousand-step session and a three-step session hand the model the same size of thing. That is a property you can state and test, not a hope you re-audit whenever a prompt gets long.

Its rendering is captured on the timeline. Every StepRecord carries ContextFixture(promptVersion, render(context)) — the active prompt version and the exact digest the model was shown. Neither is derivable from the bus alone: the prompt is an injected asset, and the digest is what an audit actually needs when someone asks why did the agent decide this? It also turns the fixture into a check. On replay, the harness re-derives each step's digest from the state that preceded it and compares it against the one committed — so a change to projectContext that silently alters what the model saw fails the golden trace, without anyone re-running the model.

Why this belongs beside the view projection, not inside the prompt

Both maps take the same argument and return formatted primitives for a consumer that must not think for itself; they differ only in who is reading. project answers “what should the person see?” and projectContext answers “what should the reasoner see?”, and each block contributes its lines to the second the same way it contributes its rows to the first. Treating the reasoner's input as prompt-assembly rather than as a projection is what leaves it untyped, unbounded and uncaptured — the one seam in the system with no test layer, feeding the one component that is not deterministic.

D

Why the context is read-only, and the result returned

The discipline has two halves and they are the same idea seen from both ends. Inbound: ctx is written once by the boundary and is read-only to tools. Outbound: the result leaves by the return value and is folded at the boundary. Put together, a tool has exactly one channel in (read ctx + take input) and exactly one channel out (return a payload). No hidden side channel exists, because none is reachable: the tool was never handed a mutable reference to anything.

This is the inversion. Naively, a tool that needs to “set priority” would hold the store and write to it. Here it cannot — it is given a read-only ctx and asked to describe the outcome as data. The capability to actually change state is not in the tool's hands; it is in the fold's, reached only through the value the tool returns. Control flows outward (the boundary acts on the result), but the source dependency points inward (the tool depends on result types and on ctx's shape, and on nothing outer).

The payoff is two properties stated plainly. Testing collapses to a function call: with no mutable context to mock and no effects to intercept, you assert run(input, ctx) == expected and you are done — no model in the loop, no surface, no doubles. Extension is local: a new capability is a handful of appended declarations, every one named by the compiler or by a check, none of them a rewrite of shared logic — the ToolResult case, the Command case, a registry entry and a fold arm, three files, one folder, and the compiler names the ones you forget. (One folder is not one module: where a language seals a hierarchy within a module, the two transport cases are authored in the shared core, so the same folder spans two directories, and each reference port states its own measured count in its own README.) You do not thread a new method through a store, a controller, and a presenter. And the count does not depend on what the verb is about: adding setPanel costs exactly what adding setPriority costs.

The Input Port, and the pre-staged request

In Clean Architecture the Input Port is the interface the controller calls to pass the Request Model in. The example keeps that split but stages it: the verb's run signature is the Input Port — the inner-side seam the agent invokes — and ctx is the Request Model, derived as ambient data before the step rather than handed across at call time. That staging is exactly what makes a verb a pure function: there is nothing to call back through, only data to read and a value to return.

E

What breaks without it

The seam earns its keep only against the version that omits it. Here is the most tempting violation — a verb that writes its result where it stands, into the context, instead of returning it:

Collapsed — the verb writes its result into ctx

VERB setPriority = Reversible {
  run(input, ctx) -> { ctx.state.tickets[input.ticket].priority = input.level }  // mutates ctx, returns nothing
}

It looks shorter — but ctx is read-only (the seam's one rule), so the write lands on the snapshot the boundary discards when the step ends: the priority never actually changes, and nothing is recorded. The test that dies: replayTest. The fold receives no result, so it produces no new state and no LogDecision effect; the committed StepRecord no longer contains the priority change at all. A re-fold of the committed bytes therefore yields a different state than the live run had — and if the mutation had somehow stuck in the live process, replay would diverge from reality while looking perfectly healthy. This is Hidden State Coupling: the result took a side channel the recorder cannot see. You did not save a line; you deleted replay.

Collapsed — the verb stamps the actor

VERB confirmEscalation = Irreversible {
  run(input, ctx) -> ConfirmEscalation { ticket: input.ticket, by: ctx.actor }  // records the confirmer
}

This is the one that reads as diligence. Give ctx an actor, let the result carry by, and the fold can gate on it — a whole authorization story assembled out of pieces that each look responsible. What you have actually built is two authorship values per step that nothing reconciles: the one this verb copied, and the one the boundary stamps afterwards. The gate reads the first; the audit log records the second; and the moment an injected instruction or a bad inference moves one of them, the log is truthfully reporting a decision that was made on a forged premise. What dies is not a test. Replay stays green — it faithfully re-folds the forged value. What dies is the record's meaning. The fix is not care: it is that ctx has exactly two fields and no ToolResult case may hold an Actor, so this listing does not compile. The verb reports what, and the boundary alone reports who.

Collapsed — the verb returns a live handle

If run returns the live Ticket object (or a socket, or a file handle) instead of a ToolResult value, the boundary now holds something it can mutate and the world can change underneath. The payload is no longer a record of what happened; it is a leak of where it happened. Replay cannot reconstruct it — a handle is not data — and a re-fold of the recording disagrees with the live run because the thing behind the handle moved. The DTO rule exists to make this impossible: a verb may return only a closed, inert value.

All three failures share a shape: the verb tried to act or to attest — to write, to name the caller, to hand out a live thing — instead of describing the outcome as data it returns. The seam exists precisely to make that the only move available, so the recorder sees everything, the stamp has one source, and the re-fold never diverges.

F

The test that the seam makes possible

Because a verb is a pure function of input and a read of ctx, it is tested by direct call — no model, no surface, no mock of a mutable context, no doubles at all. The context projection is tested the same way, because it is the same kind of thing:

testing a pure verb, and the projection behind ctx — direct callspseudocode
test "setPriority is a pure function of its input":
  ctx = Ctx(state = oneOpenTicket(4118), context = projectContext(oneOpenTicket(4118), null))
  assert setPriority.run({ ticket: 4118, level: High }, ctx)
         == SetPriority(ticket: 4118, level: High)        // returned, not written

test "focusTicket is the same mechanic, tested the same way":
  assert focusTicket.run({ ticket: 4118 }, ctx) == FocusTicket(ticket: 4118)
  assert ctx.state.tickets == { 4118: ticket(4118) }      // ctx unchanged — read-only held
  // and note what is NOT here: the verb does not check whether 4118 exists.
  // That is the fold's job, against the state it is about to write. (seam 01)

test "projectContext is a bounded projection of committed State":
  c = projectContext(stateWith(tickets = 500, notices = 200), staged = [TicketArrived(4118)])
  assert c.staged  == [TicketArrived(4118)]               // the ORDERED off-bus fixture staged for this turn
  assert c.lines.size   <= MAX_CONTEXT_LINES              // the bound holds at any session length …
  assert c.notices.size <= MAX_CONTEXT_NOTICES
  assert projectContext(s, x) == projectContext(s, x)     // recomputed, never accumulated
  assert projectContext(s, x, ContextBounds(2, 2)).lines.size == 2   // the window ARRIVES:
                                                          // the block declares a bound, the ROOT picks the number

The first test is the canonical one: setPriority.run({4118, High}, ctx) == SetPriority(4118, High), a plain equality on values. The second shows the symmetry — the presentation verb is tested identically, because it is the same mechanic — and it also shows the division of labour: the verb does not ask whether the ticket exists, because validating a transition against the state it is about to write belongs to the arm that writes it. The third is the seam that used to have no test at all: the reasoner's input, asserted by value and pinned to its declared bound.

No model emits any of these calls; no boundary commits anything; no effect fires. That is the whole gift of the seam: the unit of work the agent invokes is a value-in, value-out function, so the test is an equation. The impure work — resolving the open name, stamping, gating, recording, folding, performing — lives one seam outward, at the boundary adapter, which is the one object tested with doubles. Everything here is pure, and pure things are tested by asking them a question and checking the answer.
